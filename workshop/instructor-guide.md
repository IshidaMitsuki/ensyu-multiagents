# 講師用ガイド

## この演習で伝えること

マルチエージェント開発は、AIを魔法の自動開発者にする話ではありません。大事なのは、作業を役割に分け、各役割に必要な文脈だけを渡し、成果物を人間が検証する流れを作ることです。

この教材では、VS CodeとGitHub Copilot Chatだけで以下の流れを作ります。

```text
Planner -> Implementer -> Tester -> Reviewer -> Documenter
   |            |            |          |            |
   +------------+------------+----------+------------+
                workshop/agent-log.md
```

## Copilot Student前提の注意

- 利用可能なモデルは受講者のアカウント状態、学校認証、GitHub側の提供状況で変わります。
- 演習では「特定モデルでないと解けない課題」にしないでください。
- まずはデフォルトまたは軽量なモデルで実行し、詰まったときだけ高性能モデルに切り替える運用が安全です。
- リクエスト上限がある場合に備え、1人1役ではなく、2から3人で1つのワークスペースを共有しても成立します。

## 推奨進行

### 0. 導入

受講者に次を伝えます。

- AIの出力は提案であり、採用判断は人間が行う
- エージェントごとに「得意な失敗」が違う
- 共有ログがないと、役割分担はただの単発チャットになる

### 1. 起動確認

`app/index.html` を開きます。タスク追加、状態変更、削除、再読み込み後の保存を確認します。

### 2. Planner

Plannerには実装させません。ここで実装を始めた場合は、プロンプトの境界を守る重要性を説明します。

良いPlanner出力の条件:

- 改善が1つに絞られている
- 受け入れ条件がブラウザで確認できる
- 変更対象ファイルが少ない

### 3. Implementer

実装後に必ず差分を読ませます。差分を読まずに次へ進まないでください。

見るポイント:

- 関係ないリファクタが入っていないか
- 保存済みデータとの互換性があるか
- UIが狭い画面でも崩れにくいか

### 4. Tester

Testerには「正常に動くか」だけでなく、「壊すとしたらどこか」を聞きます。

例:

- 空文字
- 長い文字
- 状態変更を何度も行う
- 削除後に再読み込みする
- スマホ幅で操作する

### 5. Reviewer

Reviewerの指摘は、すべて採用する必要はありません。演習の範囲、リスク、再現性を見て判断させます。

### 6. Documenter

最後に、実装内容を人間の言葉で説明させます。ここで「作った本人が説明できないAI生成物」を防ぎます。

## 代替課題

時間や受講者の習熟度に応じて、Plannerに以下のどれかを指定しても構いません。

- 初級: タスク数のサマリーを改善する
- 初級: 完了タスクをまとめて削除する
- 中級: 優先度を追加する
- 中級: 検索欄を追加する
- 発展: 締切日を追加し、期限切れを強調する

## よくある詰まり

### Copilotがカスタムエージェントを認識しない

`.agent.md` ファイルの本文をCopilot Chatに貼り付けても演習は成立します。機能差で止めないでください。

### Agent Modeで大きく変更しすぎる

「変更対象ファイルを `app/app.js` と `app/index.html` だけにしてください」のように制限を追加します。

### 受講者がレビューを飛ばす

レビューを飛ばした場合、AI開発の一番重要な「受け入れ判断」が抜けます。最低1つは指摘を読み、人間が採用または却下する判断を残させてください。
